# Agent Room v2: Agentverse

Plan for turning the user's "Agentverse" brief (2026-11-18) into the app, written
after the first 3D workspace shipped (PLAN.md M17). PLAN.md stays the record of
decisions and history; this file is the v2 roadmap. Each phase ends in a check.

## 1. Goal and the hard constraint

Goal: when you open the app you see a small space-station HQ already alive. You give
Claude a task and watch the agents organise themselves, visit stations, delegate,
hand over results, all driven by what Claude Code really does.

Hard constraint (the user's): the app stays usable as an always-on companion. It must
not draw much power. Budget, measured with the release build on the user's M2:

| State | CPU (one core) | Memory |
|---|---|---|
| No Claude activity, 2D | ~0 % (sleeps) | ≤ 250 MB |
| No Claude activity, 3D (idle clip at ~4 fps) | ≤ 3 % | ≤ 250 MB |
| Claude working, window unfocused | ≤ 10 % | ≤ 250 MB |
| Claude working, window focused | ≤ 25 % | ≤ 300 MB |

Baseline today (measured 2026-11-18, release build, 3D view, unfocused): 19 % CPU and
212 MB with **no** activity, 20-33 % during a replay. 2D idles at about 0 %. The 3D view
never sleeps because the robots' idle animation keeps it redrawing. Fixing that is
phase 0, before any new feature.

## 2. Engine decision: stay on Bevy (not React Three Fiber)

The brief asks for React Three Fiber and Three.js. We stay on Rust and Bevy:

- **Power.** R3F needs a browser engine: Electron (a Chromium per app, typically
  300+ MB) or Tauri (the system WebView, lighter). A WebGL page also lacks the fine
  control we already use: sleep until an event arrives, 10 fps when unfocused, render
  only on change. Bevy gives us a native Metal app with that control today.
- **It already works.** Hooks, permission answers, the channel, mini mode, the 3D HQ
  with Blender-made robots, stations and environment, bloom, activity holograms,
  light trails and the HUD are all built and checked in Bevy.
- **The brief's real requirement is architectural**, and it holds in Bevy: the
  backend says what happened, the front end decides how to show it (section 4).

What R3F would give: drei helpers, a big ecosystem of effects, and HTML/CSS panels that
are quicker to style than egui. If panel polish in egui becomes the bottleneck, the
fallback is to keep Bevy for the world and render panels in a WebView overlay, not to
move the whole app. Revisit only with a measured prototype (same scene, same budget).

## 3. What the data can honestly show

Rule from the brief: never fabricate activity. What Claude Code gives us:

| Brief asks for | Source | Status |
|---|---|---|
| Read / write / run / search / web | `PreToolUse` / `PostToolUse` tool name and input | have |
| Subagent spawned, done, its task and report | `SubagentStart` / `SubagentStop`, `Agent` tool input | have |
| Delegation and handover | `Agent` tool call (parent → child), `SubagentStop` | have |
| Waiting for input | `PermissionRequest`, `Notification`, `AskUserQuestion` | have |
| Errors | `PostToolUseFailure`, `StopFailure` | have, not shown yet |
| Current task | the user's prompt (`UserPromptSubmit`) | have |
| Tokens, cost, latency per step | transcript JSONL (`message.usage`, tool `durationMs`) | readable, not wired |
| Messages between agents | `Agent` input (task) and the sub-agent's final report | have (two per child) |
| Task dependencies, % progress | nothing | **not available**: show steps done / running, never a made-up % |
| Agent "thoughts" | nothing (hidden) | abstract "thinking" visual only, no fake text |

## 4. Architecture

```
hooks ──► room-hook ──► socket ──► RoomEvent (room-proto)
                                      │
                                      ▼
                         Model (sessions, agents, poses)   ◄── one source of truth
                                      │ Change
                     ┌────────────────┼──────────────────┐
                     ▼                ▼                  ▼
               2D scene          Director (3D)       History (new)
            (mini, fallback)   stations, routing,   ring buffer of events
                               capsules, holograms   + time, for replay
                                      │
                                      ▼
                       3D layers: environment │ stations │ agents
                                      │
                                    HUD panels (egui)
```

- **Model** stays the only state. The 3D view stops following 2D entities: a
  **Director** turns `Change`s into per-robot intents (go to station, hand over,
  wait, error) and plays them. This removes the 2D scene as a hidden dependency of
  the 3D one (today `view3d` reads 2D `Agent` entities and the `Roster`).
- **Intent per robot, newest wins.** Events can arrive faster than a robot walks.
  Each robot keeps only its newest intent, so it never replays stale steps, and short
  tool calls (under ~1.5 s) update the hologram without a walk, like `MIN_DWELL` in 2D.
- **History** records every `RoomEvent` with its time, in memory and in
  `~/.agent-room/history/<session>.jsonl`. Replay feeds the same pipeline from that
  file at a chosen speed, so live and replay cannot drift apart.
- **Layers stay separate files** (already true): `environment/*.glb`,
  `stations/*.glb`, `robot/robot.glb`, each with its Blender script in `tools/blender/`.

## 5. Phases

Each phase lists its features, its check, and a resource note.

### Phase 0: sleep when nothing happens (power first)

- 3D redraws at full rate only while something changes: walking, a hologram growing,
  a capsule flying, a permission countdown. With nothing happening, the idle clip
  keeps playing at about 4 fps (the user's choice), so the HQ looks alive but cheap.
- Pulse effects (rings, orbs, documents) stop when unfocused.
- Build the lever: `scripts/measure.sh` runs the release build, replays the spike
  log, samples `top`, and prints idle and active CPU and memory. Every later phase
  reruns it.

Check: `scripts/measure.sh` meets the budget table (idle 3D at most 3 %, active
unfocused at most 10 %).

Result (2026-11-18, release build, unfocused, `scripts/measure.sh`):

| State | Before | After |
|---|---|---|
| Idle, first 30 s (idle clip at 4 fps) | 21.7 % | 8.5-9 % |
| Idle after 30 s (dozing: no redraws) | 21.7 % | **0.3 %** |
| Active (spike replay at 4x) | 32-35 % | 22-23 % |

- A 3D frame costs about 20 ms of CPU however little moves (`AGENT_ROOM_FPS_LOG=1`
  confirmed 4.2 fps idle at about 9 %). `sample` shows no single hotspot: thread
  wake-ups, the ECS executor, Metal command encoding and the audio callback.
- So the idle clip plays for 30 s after the last activity, then the robots doze and
  the app sleeps until a hook event or input (the user's "few fps" kept where it is
  seen; 0.3 % the rest of the time).
- Three task-pool threads instead of one per core: active 35 % to 22 %. A fully
  single-threaded executor and turning shadows off made no measurable difference.
- egui (HUD, labels) costs about 6 % while active.
- Not met yet: active unfocused at most 10 %. Next levers, in order: drop the 2D
  scene (its systems, text layout and shapes still run under the 3D view; phase 1),
  draw robot labels and HUD only when they change, and the audio output thread
  (only with sound on).

Follow-up (2026-11-18, the user: "an app like a widget, nice to look at but not the
main working app"): pacing is now a `Pace` table in `main.rs`: moving (walking,
beaming, camera) 30 fps focused / 6 unfocused, working in place 8 / 4 fps, idle
4 fps for 30 s, then dozing (no redraws). Robots stay 2.5 s at a station before
walking on (newest wins after that). `scripts/measure.sh` replays at real speed by
default now (4x made robots walk nearly all the time). Measured, release,
unfocused: working about 15-17 % (was about 27 %), idle 30 s about 9-12 %, dozing
0.3-0.5 %, about 200-300 MB. Experiments with no measurable effect (within the
3-5 point run-to-run noise): bloom and MSAA off, shadows off, 1x pixel density,
pipelined rendering off, 1, 2 or 4 worker threads (1 was worse). A frame costs
about 16 ms user plus 8 ms system CPU whatever it draws, so frame count is the
lever. The 10 % working budget is not met; the next step would be fewer frames
again (for example 4 fps working even when focused) or a much cheaper scene.

### Phase 1: the Director and a truthful event map

- `director.rs`: `Change` → robot intents. The tool-to-station map lives in one
  table: Read/Grep/Glob → reading station, Edit/Write → writing desk, Bash/MCP → lab,
  WebSearch/WebFetch → research station, `Agent` → delegate, `SubagentStop` →
  handover, permission/question → waiting, failure → error.
- Robots no longer read 2D entities; avatars are keyed by agent id.
- **Delete the 2D view** (the user, 2026-11-18: "we can remove 2d completely, 3d is
  so nice now"): `scene.rs`, `anim.rs`, `camera.rs`, lyon shapes, the 2D/3D switch
  and `AGENT_ROOM_VIEW3D`. Mini mode is 3D already. Measure the gain.
- Errors: a red ring and a warning icon over the robot until its next success.
- Tests feed a recorded event log and assert the intents (a pure function, no
  rendering).

Check: tests green; the spike replay looks as it does today in 3D; `scripts/measure.sh`.

Result (2026-11-18): done. `director.rs` (`cast`, `location_for`, tested with a
recorded turn) drives `view3d`; robots are keyed by `Who` and session. 2D is gone
(scene, anim, camera, theme, lyon, the Nunito font; about 2,000 lines). Errors and the
short-call dwell are not in yet (move to phase 3). `scripts/measure.sh`, release,
unfocused: idle 9 % to 5.3 %, dozing 0.4 %, active 22.7 % to 14.8 %, peak memory
about 470 to 270 MB. Active is still over the 10 % budget; next levers: draw the HUD
and labels only when they change, and the audio thread.

### Phase 2: stations the brief adds

- Split "Bookshelf" into a **Reading station** (files) and a **Research station**
  (web: floating cards, a small knowledge-graph hologram).
- Handover: the user decided on 2026-11-17 to hand over at the main desk. Keep that,
  and give the main desk a small handover ring in front, so the brief's "space for two
  robots" exists without a separate trip.
- Blender: `stations.py` gains `research.glb`; the floor rings move. (Docking bays
  are dropped: the teleporter in phase 3 is where agents arrive and leave.)

Check: screenshots from the app camera with every station in view.

Result (2026-11-18): done together with the teleporter and phase 3b. The bookshelf
is the reading station (Read, Grep, Glob); a new Research station
(`tools/blender/research.py`, amber knowledge-graph console) replaces the file-reading
desk for WebSearch and WebFetch. The teleporter stands front left; robots beam in
and out of it with a presence state machine (Arriving, Here, Departing, Boarding,
Leaving), one robot on the deck at a time, the others waiting round it. Every live
session's Claude has its own seat at the main desk and colour, and labels name the
project when there are several; clicking a robot's label shows its session's
panels. The HUD stage strip was dropped (the user: it looked bad and its fixed order
was not real). Power, A/B on the same machine: phase 1 build idle 9.0 % / active
21.2 %, this build 7.9 % / 20.7 %; runs vary by about 4 points, so phase 1's 5.3 /
14.8 was a lucky run. Not done yet: the beam is a plain show/hide, no particles.

### Phase 3: spawning, delegation, handover, communication

- **Teleporter** (the user's brief, 2026-11-18, with a reference image of a tiered
  round dais with a beam): a platform in the HQ where every agent arrives and leaves,
  sessions and sub-agents alike. Model: `tools/blender/teleporter.py` writes
  `stations/teleporter.glb` with named moving parts (`Ring0..2`, `Beam`,
  `Orbiters`), recoloured per agent type through its `Energy` material.
  - Arrive (session started or sub-agent started), about 2.5 s: rings spin up, beam
    forms, the robot materialises (scale and emissive fade in), an activation nod,
    its name label appears, then it walks to its station.
  - Leave, about 2.5 s: only when the session really ends (`SessionEnd`) or the
    sub-agent stops (`SubagentStop`, after its handover). A finished turn is not a
    departure: the agent stays. Failure: a red flash before it leaves.
  - Arrivals at the same moment queue one after another; the platform has one robot
    at a time, others wait in a ring around it.
  - A small state machine per robot (Arriving, Working, Leaving, Gone) so an event in
    the middle of an animation interrupts or resumes it safely.
  - Effects stay cheap: a few dozen instanced particle quads, emissive meshes and
    bloom; no custom shaders or GPU particle engine. Frozen when dozing.
- Delegate: the main robot turns to the new one, and a task capsule flies over on a
  glowing arc with a few particles (a handful of instanced quads, no particle engine).
- Handover: the sub-agent walks back, and the capsule flies to the main robot.
- Communication line: parent ↔ child line while the child works, brighter while data
  moves.

Check: a replay with two sub-agents; screenshots at each beat.

Result (2026-11-18): done. `view3d::links`: a glowing line from each working
sub-agent to its session's Claude; a task capsule (`holo_capsule.glb`) flies on an
arc from Claude to a sub-agent once it has beamed in, and its report flies back at
hand-over (to the inbox when Claude is away); a red ring and a red label under any
robot whose last tool call failed, until a call succeeds (`model::failure`, tested
in `director`). Every robot now thinks and waits where it stands (sub-agents no
longer walk back to Claude between tool calls). Measured: dozing 0.1 %, active
18 %. Not done: particles along the line while data moves.

### Phase 3b: every session in one HQ

- Each live session's main robot arrives through the teleporter and works from the
  main desk ring (own slot), tinted with the session's colour, its name label showing
  the project folder.
- Its sub-agents and station visits share the same stations (slots already allow five
  robots per station).
- Ended sessions' robots walk to the teleporter and leave.

Check: two `claude` sessions replayed at once; both visible, labels distinct.

### Phase 4: panels and the timeline

- Top bar (exists): add total spawned agents and a settings button.
- Right panel: agent list (name, role, current task, status, parent, runtime);
  clicking one highlights its robot (ring + camera focus).
- Bottom: a chronological event stream with icons; click an event for its details
  (tool input and result from the hook payload).
- Agent details (exists): add tool calls with input and output, parent and children,
  errors.
- Notifications: small toasts for spawned, completed, handover, failed, waiting.
- Minimap: a 2D egui overview drawn from station and robot positions (cheap; no
  second 3D camera).

Check: screenshots; every panel works with two sessions and with none.

Result (2026-11-18): done, trimmed for a widget. Notifications (`notify.rs`): a
toast bottom right for an agent joining, handing over, failing, needing the user,
and Claude done; 5 s, at most four, a burst of the same one shows once. Sound is on
by default with one "Sound on/off" button (saved in `ui.json`); sounds are macOS
system sounds played by `afplay`, one short process each, so nothing runs between
them (Bevy's audio stream stays off). The side panel's log is the event timeline
(no second strip over the HQ). The minimap was built and then removed: the user
did not want it.

### Phase 5: camera and time machine

- Orbit, pan and zoom (mouse and trackpad), reset, focus on and follow an agent.
- Cinematic mode: follows the latest meaningful event, at most one cut every few
  seconds.
- Time machine: pause, rewind, replay at 0.5× to 8× from History (section 4).

Check: a replay from the history file matches the live run in screenshots.

Result (2026-11-18): trimmed by the user ("we dont really need phase 5, maybe pan
and zoom"). Full view only: drag to pan, scroll or pinch to zoom, double-click to
reset (`view3d::camera_input`, only over the HQ, never over a panel). No orbit,
follow, cinematic mode or replay.

### Phase 6: operations room and polish

- Operations room (toggle): tokens, cost estimate, tool-call counts and durations,
  errors per agent, read from the session transcript (`transcript_path`).
- Atmosphere within budget: a few slow dust motes, holo flicker, window stars; all
  frozen when unfocused.
- Optional and measured: volumetric fog (built into `bevy_pbr`) and cheap
  reflections (an environment map), only if they fit the focused budget.

Check: `scripts/measure.sh` after each item; drop anything over budget.

Result (2026-11-18): trimmed for a widget. The counts card shows the session's
tokens (in, cache included, and out), read from the transcript only when a turn
ends and only the new part (`usage.rs`, tested). No cost estimate (prices differ by
model and plan; it would be a guess). No extra atmosphere: every effect costs frames.

## 6. Ideas that make it more fun to use

Picked from the brief and ranked by delight per cost:

1. **Follow cam on click** (phase 5, cheap): click a robot and the camera follows it.
2. **Time machine** (phase 5): rewind a finished turn and watch it again at 4×.
3. **Docking bays** (phase 2): finished sub-agents walk to a charger and power down
   instead of vanishing.
4. **Trophy shelf**: one glowing cube per finished turn of the day; click one to read
   that turn's final answer.
5. **Sound** (on by default, mute and off in the HUD): soft blips for spawn, handover
   and permission requests.
6. **Every session in one HQ** (phase 3b): all live Claude sessions work side by side.

## 7. Out of scope for now

- Task dependency graphs and % progress (no data; it would be invented).
- Screen-space reflections and heavy volumetrics by default (power budget).
- A web front end (section 2).

## 8. Decisions (the user, 2026-11-18)

- **Idle 3D**: keep a slow idle animation at a few fps (target 4 fps) instead of
  freezing. Phase 0 budgets it: idle 3D must still stay near 0 % (≤ 3 %).
- **Sessions**: no wings. Every live Claude session spawns its main robot in the
  same HQ, sharing the stations; each session's robots carry its colour and name.
  The HUD switcher stays for the panels (which session the timeline and cards show).
  Planned as phase 3b.
- **Sound**: on by default. The HUD has a mute button and an "off" setting; off
  drops the audio output entirely (no audio thread) to save power; teleporter sounds
  follow the same switch. Planned with
  phase 4 notifications.
- **Idle in practice** (phase 0 measurement): the idle clip plays for 30 s after the
  last activity, then the robots doze (0.3 %); 4 fps forever would cost about 9 %.
- **No 2D**: the 2D view goes in phase 1, once the Director drives the robots.
- **Teleporter**: every agent, sessions included, arrives and leaves through it
  (phase 3). Agents leave only when their session or sub-agent really ends.
- **Claude stays put** for a new message: it says "On it!" where it stands and only
  walks home when the turn ends (fixed 2026-11-18, `view3d::location_for`).
